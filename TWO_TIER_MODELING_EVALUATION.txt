1. WHAT IS THE TWO-TIER APPROACH?
==============================================================================

The Club Piscine forecasting pipeline uses TWO SEPARATE neural models:

TIER 1 (Units Model):
- Target: UNITS (items sold per week, per store×division)
- Algorithm: LightGBM regression
- Performance: R² = 0.936 (full), wMAPE = 0.212 (test)
- Cross-validation: Walk-forward, 6 folds, wMAPE = 0.233 ± 0.091
- Features: units lags (1w, 2w, 4w, 52w), rolling means/stds, demand volatility,
  seasonal/calendar terms (Fourier, month, quarter, season flags), weather
  (temp, precip, sunshine, lags), activity metrics

TIER 2 (Revenue Model):
- Target: REVENUE (dollars, per store×division)
- Algorithm: LightGBM regression (SEPARATE model, not Tier 1 output × price)
- Performance: R² = 0.805 (full), wMAPE = 0.329 (test)
- Features: SAME as Tier 1, PLUS revenue-specific features
  (revenue lags, avg_price_per_unit, revenue rolling stats)
- Confidence intervals: Quantile regression (P5/P95) for both

Critical Distinction:
The approach does NOT cascade (units → revenue). Instead:
- Tier 1: Predict units independently
- Tier 2: Predict revenue independently, as a separate supervised learning task
- Both models use overlapping but not identical features
- Combined output: (predicted_units, predicted_revenue) pairs per group

This is NOT a true "two-tier" model in the traditional supply chain sense.
It's really a "DUAL-TARGET" approach: two independent LightGBM models
trained on the same store×division groups with different objectives.

2. IS IT VALID?
==============================================================================

ARGUMENTS FOR (Pros):
────────────────────

a) Product Mix Heterogeneity:
   - Club Piscine sells pools ($50–$30K+), spas, furniture, fitness, BBQs
   - Average price varies enormously by week (e.g., $5K spa vs $16K pool)
   - Simply multiplying predicted units by lagged price BREAKS under high variance
   - Direct revenue model learns implicit price dynamics from revenue_lag_1w,
     avg_price_per_unit features

   Evidence: Old approach (units × price_lag_1w) = wMAPE 0.795 (poor)
             Direct revenue model = wMAPE 0.329 (3.7× better)

b) Feature Richness:
   - Both models use 40+ features: demand, weather, seasonality, activity
   - By treating units and revenue as separate targets, each model can learn
     target-specific non-linearities
   - Units respond to seasonality/weather differently than revenue
     (e.g., May barbecue promotion: high unit volume but low $ per unit)

c) Prediction Intervals:
   - Quantile regression gives honest 90% CIs for both targets
   - No error propagation needed (unlike cascade approach)

d) Industry Precedent:
   - Retail forecasting often uses dual targeting when:
     * Product mix is volatile (✓ here)
     * Price and volume are not orthogonal (✓ here)
   - Examples: grocery retail (units + revenue), e-commerce (quantity + AOV)

ARGUMENTS AGAINST (Cons):
─────────────────────────

a) No Economic Constraint:
   - Units and revenue models are completely independent
   - Mathematically, nothing prevents:
     predicted_revenue > predicted_units × max_historical_price_per_unit
     OR
     predicted_revenue < predicted_units × min_historical_price_per_unit
   - No feedback loop to enforce Revenue ≈ Units × Price
   - In production, if units spike but revenue model predicts flat, planner gets
     contradictory signals

b) Error Non-Compounding, But Incoherence:
   - If units wMAPE = 21%, revenue wMAPE = 33%, forecast error is NOT 54%
   - But units and revenue forecasts can be INCOHERENT
   - Example: predict 100 units, predict revenue = $500 → implied price = $5/unit
     If true avg price is $2,000/unit, this is nonsensical for inventory/
     revenue reconciliation

c) Feature Leakage/Circularity:
   - Revenue model includes avg_price_per_unit, which is computed from revenue
   - If price is autocorrelated (it often is), this feature dominates
   - Creates a form of self-prediction: revenue predicts revenue

d) Small Sample + Multiple Targets:
   - Only 36 months of data (156 weekly obs, aggregated to monthly in MMM)
   - Here: 156 weekly observations across 284 store×division groups (0.55 obs/group avg)
   - Training one model per group would overfit; global model dilutes signal
   - Adding a second model (revenue) adds complexity without increasing data

WHAT ACADEMIC/INDUSTRY LITERATURE SAYS:
─────────────────────────────────────────

Hierarchical Forecasting (Rob Hyndman et al., 2016+):
- AVOID independent forecasts of components that should sum
- Recommends: Forecast top level (total revenue), then disaggregate
  OR forecast bottom level (units), then aggregate to revenue via price index

Product Mix Models (IRI, Nielsen, Accenture research):
- When product mix is volatile:
  * Option A: Forecast units, use stable price index (fails if price really volatile)
  * Option B: Segment by product class, forecast separately, reaggregate (complex)
  * Option C: Forecast revenue directly, leave units as derived metric (inverse wMAPE)
- Most retail practitioners prefer C for highly heterogeneous portfolios

Supply Chain / Inventory Literature:
- "Bullwhip effect": Forecast errors compound upstream
- Dual forecasting (units + revenue) only works if linked via:
  1. Explicit price model (e.g., regression on demand/seasonality)
  2. Constraints/post-processing to enforce coherence
- Without linking, separate models are risky for operations

VERDICT:
┌─────────────────────────────────────────────────────────────────────────┐
│ PARTIALLY VALID, WITH CAVEATS                                           │
│                                                                           │
│ ✓ Pragmatic for forecasting accuracy (revenue wMAPE = 33% is good)       │
│ ✓ Handles product mix heterogeneity well (superior to units × price)     │
│ ✗ Creates forecast incoherence (units and revenue can be misaligned)     │
│ ✗ Lacks economic constraint (no guarantee coherence)                     │
│                                                                           │
│ RECOMMENDATION: Use only if downstream process validates coherence       │
│ (e.g., planner reconciles units ↔ revenue before inventory action)       │
└─────────────────────────────────────────────────────────────────────────┘

3. ERROR COMPOUNDING ANALYSIS
==============================================================================

Claim: If Tier 1 (units) has 20% MAPE and Tier 2 (revenue) has 10% MAPE,
       combined error is NOT 30%.

Analysis:
──────────

Define:
- U_actual = true units (e.g., 100)
- R_actual = true revenue (e.g., $50K)
- U_pred = predicted units (e.g., 80)
- R_pred = predicted revenue (e.g., $45K)
- P_true = true average price = R_actual / U_actual = $500/unit

Unit Error:
- MAPE_units = |U_actual - U_pred| / U_actual = |100 - 80| / 100 = 20%
- U_pred is 80% of actual

Revenue Error:
- MAPE_revenue = |R_actual - R_pred| / R_actual = |50K - 45K| / 50K = 10%
- R_pred is 90% of actual

Combined Metric (Implied Price):
- P_implied = R_pred / U_pred = 45K / 80 = $562.50/unit
- Actual price = $500/unit
- Price error = ($562.50 - $500) / $500 = 12.5% OVERESTIMATE

Why Not 30%?
━━━━━━━━━━━━
The errors don't add linearly because:

1. Units and revenue errors can have different signs/magnitudes
2. If units undershoot (80) but revenue overshoots (45K forecast for 50K actual
   would be +10%), the implied price = 45K/80 = $562.50, which actually
   INCREASES from true $500
3. Error propagation in ratios: E[R/U] ≠ E[R] / E[U] (Jensen's inequality)

The correct analysis uses conditional expectations:
  E[P_implied | U_pred, R_pred] = E[R_pred / U_pred]

This is NOT simply E[R_pred] / E[U_pred] = 45K / 80.

In the Club Piscine context:
────────────────────────────

Actual results (NB05 test set):
- Units wMAPE = 21.2%  (R² = 0.936)
- Revenue wMAPE = 32.9% (R² = 0.805)

Implied Price Accuracy:
- Since wMAPE is weighted by actual magnitude, not proportional error:
  wMAPE(revenue) ≠ wMAPE(units) + wMAPE(price)

- wMAPE aggregates errors across all groups:
  wMAPE = Σ|actual - pred| / Σ|actual|

- If units forecast error = 20 units, revenue forecast error = $5K, then:
  Revenue_error = Units_error × Price ± Price_error × Units

- If price varies a lot, the Price_error × Units term dominates

CONCLUSION: Error compounding is SUBLINEAR but NOT negligible.
A 20% unit error + 30% revenue error ≠ 50% combined error, but the implied
price will be biased, typically 10–25% depending on whether errors are
correlated or independent.

4. WOULD A SINGLE-STAGE MODEL (REVENUE ONLY) BE BETTER?
==============================================================================

Question: Should Club Piscine just forecast revenue directly and derive units
          as (revenue / price_lag_1w)?

Analysis:
──────────

Single-Model Approach (Revenue Only):
────────────────────────────────────

Pros:
  ✓ One model to train, validate, monitor
  ✓ Automatically coherent: no mismatch between units & revenue
  ✓ Simplifies downstream inventory planning (use revenue forecast directly)
  ✓ Better for finance/planning (top-line dollar forecasts)

Cons:
  ✗ Loses units signal
  ✗ Can't forecast unit demand (needed for:
      - Inventory count (units, not $ value)
      - Promotion planning (units on sale)
      - Supplier purchase orders (units, not $)
  ✗ Revenue model alone achieves R² = 0.805, wMAPE = 0.329
    Units model achieves R² = 0.936, wMAPE = 0.212 (much better)
  ✗ Inventory gap analysis in NB04 specifically needs UNITS

Reverse Approach (Units Only + Derived Price):
───────────────────────────────────────────────

Pros:
  ✓ Units forecasting is very accurate (R² = 0.936)
  ✓ Can predict unit demand for supply chain
  ✗ FAILS when deriving revenue from units × price_lag_1w
    - Old approach (shown in NB05): wMAPE = 0.795 (terrible)
    - Reason: Price is too volatile (product mix changes)

Hybrid Approach (What Club Piscine Does):
─────────────────────────────────────────

Provides:
  ✓ Best units accuracy (R² = 0.936) for operations
  ✓ Best revenue accuracy (R² = 0.805, not cascaded error) for finance
  ✓ Separate CIs for each target
  ✗ Incoherence risk (units and revenue can diverge)

RECOMMENDATION:
───────────────

Context matters. Club Piscine needs BOTH:
- Units: For inventory planning, supplier POs, 42-store operations
- Revenue: For cash flow forecasting, budget planning, ROAS analysis

BEST APPROACH (not currently used):
  1. Forecast UNITS (LightGBM, R² = 0.936) ← Use this as primary
  2. Forecast UNIT PRICE via separate model:
     - Target: avg_price_per_unit (revenue / units)
     - Features: seasonality, product mix proxies, promotions
     - Or: Use historical price index by week-of-year
  3. Derived revenue = U_pred × P_pred (with post-reconciliation)
  4. Apply price constraints: P_pred ∈ [P_min, P_max] historically observed

Why? Separates the "volume" problem (solved well) from the "mix" problem
(which is really what matters for revenue).

ACTUAL vs. IDEAL:
│ Approach                  │ Units Accuracy │ Revenue Accuracy │ Coherence │
├──────────────────────────┼────────────────┼──────────────────┼───────────┤
│ Direct Revenue Only       │ ✗ None         │ 0.805 (good)     │ ✓ Perfect │
│ Units × Price_lag        │ 0.936 (best)   │ 0.795 (poor)     │ ✓ Enforced│
│ Dual Independent          │ 0.936 (best)   │ 0.805 (best)     │ ✗ Risky   │
│ Units + Price_Model (Rec.)│ 0.936 (best)   │ ~0.75–0.80 (ok)  │ ✓ Linked  │
└──────────────────────────┴────────────────┴──────────────────┴───────────┘

VERDICT:
Single-stage revenue model would lose critical unit visibility.
Dual approach is better, but should add POST-PROCESSING constraint.

5. DATA REALITY: PRODUCT HETEROGENEITY AT CLUB PISCINE
==============================================================================

Context (from CLAUDE.md):
───────────────────────

Products Sold:
  - Pools: $5,000–$30,000+
  - Spas: $3,000–$15,000
  - Outdoor furniture: $100–$5,000 per set
  - Fitness equipment: $500–$3,000
  - BBQs: $800–$5,000
  - Accessories: $20–$500

Price Range: ~250:1 ratio (min $50, max $30,000)

Sales Distribution (6 categories equal weight in model):
  - HT (Heating): Spas, heaters, covers
  - CR (Manuels & Contrats): Service contracts
  - SP (Services/Piscines): Pools, large items
  - ME&GA: Fitness & Accessories
  - FI (Furniture): Outdoor furniture
  - BQ (BBQs)

Seasonal Pattern:
  - Off-season (Nov–Mar): Small accessories, service contracts
  - Spring (Apr–May): Pool openers, chemicals, small items
  - Summer (Jun–Aug): Large pools, furniture, barbecues (peak season)
  - Fall (Sep–Oct): Winterization products

Revenue vs. Units Dynamics:
────────────────────────────

Example Week 1 (Spring):
- Units: 50 (pool openers, chemicals, covers, small items)
- Revenue: $8,000
- Avg price: $160/unit
- Product mix: Low-value consumables, high volume

Example Week 2 (Summer):
- Units: 25 (2 large pools, 3 outdoor furniture sets, 20 small items)
- Revenue: $42,000
- Avg price: $1,680/unit
- Product mix: High-value capital items, lower volume

Product Mix Effect:
- Same $50K revenue could represent:
  * 250 units of accessories ($200 avg)
  * OR 2 pools + 5 furniture sets + 20 small items (25 units)

Key Insight:
───────────
Price-per-unit is NOT stable. It's ENDOGENOUS to product mix, which is
exogenous (depends on season, promotions, inventory levels, customer
preferences, competitive pressure).

Implication for Forecasting:
────────────────────────────

Why Direct Revenue Model Works Better:
1. Revenue_lag_1w captures momentum in product mix (not just inflation)
2. avg_price_per_unit features encode current mix state
3. Seasonality directly predicts mix (Mar = low-value, Jun = high-value)
4. Weather (e.g., sunshine hours) predicts outdoor furniture season

Why Units × Price_lag Fails:
1. price_lag_1w is a noisy proxy for true product mix next week
2. If last week was all accessories, but this week has 2 pools, price jumps 10×
3. Lagged price can't predict next week's mix because mix is sticky on different
   timescale (day, not week)
4. Volatility explodes in multiplication: E[U × P] error >> E[U] error + E[P] error

VERDICT:
Product heterogeneity makes units × lagged price UNSUITABLE for Club Piscine.
Direct revenue model is justified. However, SEPARATE independent models still
risk incoherence—a middle path (units + product mix model) would be ideal.

Approach in NB05:
─────────────────

1. UNITS: LightGBM global regression
   - Input: 43 features (lags, rolling stats, seasonality, weather, activity)
   - Output: pred_units (point) + pred_units_lower/upper (quantile CIs)
   - Handles all 284 groups (intermittent, high-volume, low-volume)

2. REVENUE: SEPARATE LightGBM global regression
   - SAME features, DIFFERENT target
   - Output: pred_revenue (point) + CIs
   - No cascading from units prediction

   - Recursive prediction: feed prediction back as lag input
   - Outputs both units and revenue for each week-ahead

Does NB05 Fix the Incoherence Issue?
────────────────────────────────────

NO. NB05 makes the same trade-off as NB04:
  ✓ Better individual accuracy (units R²=0.936, revenue R²=0.805)
  ✗ No constraint forcing Revenue ≈ Units × Price

Differences:
- NB04: Tiered models (global XGBoost for units, Prophet for comparison)
- NB05: Two global LightGBM models (units + revenue independently)

Neither enforces coherence. NB05 just REPLACES the approach with better ML
infrastructure, not a different model structure.

Alternative Approach NB05 Considered (Not Used):
──────────────────────────────────────────────

The notebook mentions:

VERDICT:
NB05 does NOT fix the conceptual two-tier issue; it REPLACES it with a
better pragmatic alternative: dual independent models trained on the same
features. This is a better engineering choice, but still lacks the economic
constraint of a true hierarchical model.

7. RECOMMENDATION: OPTIMAL MODELING APPROACH FOR CLUB PISCINE
==============================================================================

Context:
────────
- 42 stores, 6 product divisions, 3 years of weekly data (156 obs)
- 284 store×division groups (0.55 obs/group on average)
- Strong seasonality (85% media spend Mar–Sep)
- High product mix volatility ($50–$30K range)
- Need BOTH units (operations) and revenue (finance)

Current State (NB05):
─────────────────────
✓ Global LightGBM for units (R² 0.936, wMAPE 0.212)
✓ Global LightGBM for revenue (R² 0.805, wMAPE 0.329)
✓ 100% store×division coverage
✓ Walk-forward CV, confidence intervals
✗ No coherence enforcement (units and revenue can diverge)

RECOMMENDED APPROACH (3-Tier Hybrid):
═════════════════════════════════════

Tier 1: UNITS Forecasting (KEEP CURRENT)
──────────────────────────────────────────
Model: LightGBM (global, all groups)
Target: Units sold per week
Features: Lags, rolling stats, seasonality, weather, activity
Why: R² = 0.936 is excellent; solves volume problem well

Tier 2: PRICE/MIX Model (NEW)
──────────────────────────────
Model: Linear regression or Light GBM (simpler)
Target: avg_price_per_unit = revenue / units
Features:
  - Seasonality (month, quarter, week-of-year Fourier)
  - Indicators: is_summer_peak, is_spring_opening, is_winter_off
  - Weather (temperature, sunshine → outdoor furniture season)
  - Division-specific historical price index (5-year average by week)
  - Lagged price (autoregressive, but smooth)
  - Promotional calendar (if available)
Why:
  ✓ Separates mix problem from volume problem
  ✓ Can constrain price within historical bounds
  ✓ More interpretable than revenue black-box
  ✓ Likely achieves 10–15% MAPE (reasonable for price)

Tier 3: REVENUE Reconciliation (NEW)
────────────────────────────────────
Rule: R_final = U_pred × P_pred
With constraints:
  - R_final ≥ min_historical_revenue_by_group
  - R_final ≤ max_historical_revenue_by_group
  - P_final ∈ [P_percentile_5, P_percentile_95] historically
Why:
  ✓ Enforces economic coherence
  ✓ No independent forecast can violate bounds
  ✓ Planners see units AND derived revenue together

Implementation Steps:

Why NOT Other Approaches:
──────────────────────────

❌ Separate per-group models:
   - Would have 284 separate models (maintenance nightmare)

✓ Global LightGBM (current) + Price Model (recommended):

- For price model: Expect 10–20% MAPE (enough data for seasonal pattern)
